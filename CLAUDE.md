# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

Pluma is a from-scratch Laravel rebuild of [Postiz](https://github.com/gitroomhq/postiz-app), a social-media scheduling SaaS. The original is NestJS + Prisma/Postgres + Temporal (workflow engine) + Redis + Next.js/React; this rewrite replaces that entire stack with Laravel + Blade/Livewire.

This is a rewrite, not a port of Postiz's code — Postiz is AGPL-3.0, and this app is intended to be resold as closed-source multi-tenant SaaS, which AGPL's network-use clause would not allow for a fork. Only architectural ideas are being carried over, not literal code.

The full conversion plan (backend architecture, integrations-layer design, frontend plan, phased build order) lives at `/Users/ebenezerdaniel/.claude/plans/can-you-convert-this-warm-pnueli.md`. Read it before starting a new phase of work — it defines what belongs in which phase and why.

Priority social integrations to build (before expanding to Postiz's other ~30): Instagram, Facebook, LinkedIn, YouTube, X (Twitter), WhatsApp, Snapchat. WhatsApp and Snapchat aren't in original Postiz and have real product constraints, not just implementation gaps. **Snapchat is skipped entirely** (product decision, not yet implemented): it has no public API for organic/personal post scheduling, only the Marketing API for paid ad creative — a materially different feature, not on the roadmap right now. **WhatsApp is built, but as a separate feature module** (`app/Domain/WhatsApp`), not a `SocialProviderContract`/Launches integration: its Business Cloud API sends targeted broadcast messages to opted-in contacts using pre-approved templates, not public feed posts.

## Commands

All PHP/artisan commands run **inside Docker via Sail** — do not install Postgres/Redis on the host. The app runs at `http://localhost:8090` (Postgres on 5433, Redis on 6380, Mailpit UI on 8026 — shifted off Sail's defaults to avoid clashing with other local Sail projects on this machine).

```bash
# Start/stop the stack
./vendor/bin/sail up -d
./vendor/bin/sail down

# Run the full test suite
./vendor/bin/sail artisan test

# Run a single test file / method
./vendor/bin/sail artisan test tests/Feature/PostCrudTest.php
./vendor/bin/sail artisan test --filter=test_a_post_can_be_created_and_is_scoped_to_the_current_organization

# Migrations (prefer this over migrate:fresh once a test account exists —
# migrate:fresh wipes all local data including logins)
./vendor/bin/sail artisan migrate

# Composer / npm (also run through Sail so they use the container's PHP/Node)
./vendor/bin/sail composer require <package>
./vendor/bin/sail npm run build
./vendor/bin/sail npm run dev

# Tinker
./vendor/bin/sail artisan tinker
```

No CI/lint command is configured yet (`laravel/pint` is installed as a dev dependency but has no project-specific config or script wired up).

## Architecture

### Domain-oriented structure, not the default Laravel layout

Business logic lives under `app/Domain/{Organization,Auth,Billing,Posts,Integrations}/{Models,Actions,Policies,Enums,Concerns,Support,Contracts,Providers}`, not `app/Models`/`app/Http/Controllers`. Controllers and Livewire components stay thin and call single-purpose Action classes (e.g. `App\Domain\Posts\Actions\CreatePost`). `app/Models/User.php` and Fortify's actions under `app/Actions/Fortify` are the only things left in Laravel's default locations, since Jetstream/Fortify scaffolding expects them there.

When adding a new domain, follow this same folder shape rather than flattening things into `app/Models`.

### Organization is Jetstream's Team, renamed and extended

Jetstream ships a `Team` concept (teams/team_user/team_invitations tables, a `HasTeams` trait on `User`). This app renames that to `Organization` (`App\Domain\Organization\Models\Organization`, tables `organizations`/`organization_user`/`organization_invitations`) to match Postiz's domain language, and it's also the Cashier `Billable` model (billing is per-org, not per-user) and the media library owner (see below).

**Important gotcha:** Jetstream's `HasTeams` trait and base `Team` class hardcode a handful of literal column names across several methods — `user_id` (owner FK), `personal_team`, and `current_team_id` (on `users`). These were deliberately *not* renamed even though everything else was, because doing so would mean overriding those vendor methods. If you see `current_team_id` or `personal_team` in code, that's why — it's not an oversight.

Relationship/method names inherited from Jetstream (`$user->currentTeam`, `$user->ownedTeams()`, `$organization->users()`, `$organization->teamInvitations()`) are also kept as-is rather than renamed to `currentOrganization()` etc., since Jetstream's own controllers and Blade component internals call them by these names. Only the **model class** and **user-facing Blade copy** say "Organization" — internal plumbing still says "Team" in places.

Roles are custom: `superadmin`/`admin`/`user` (defined in `JetstreamServiceProvider::configurePermissions()`), replacing Jetstream's default demo `admin`/`editor` roles. The org creator is implicitly full-access via Jetstream's "owner" concept regardless of their pivot role.

### Multi-tenancy: global scope, not a tenancy package

`App\Domain\Organization\Concerns\BelongsToOrganization` is the safety net — any model that uses it gets a global scope filtering every query to the active organization, and auto-fills `organization_id` on create. "Active organization" is resolved by `App\Domain\Organization\Support\CurrentOrganization`, which defaults to `Auth::user()->currentTeam` for normal web requests.

The scope is a no-op when no organization is resolvable (rather than hiding all rows) — this is intentional so console commands, tests, and future cross-tenant admin tooling can still query freely by being explicit. Background jobs have no authenticated user, so they must call `CurrentOrganization::set($organization)` before touching any scoped model and `clear()` afterward — see `PublishPostJob` for the pattern.

`Post` and `Tag` use this trait; `PostComment` and `PostError` deliberately don't (they inherit tenant isolation transitively through their parent `Post`).

### Media library is organization-level, not per-post

`Organization` implements `HasMedia`/`InteractsWithMedia` (spatie/laravel-medialibrary) with a `'library'` collection — this matches Postiz's model where uploaded assets are a shared org-wide library, not owned by individual posts. `Post` also implements `InteractsWithMedia` separately, registering a `'default'` collection via `registerMediaCollections()` with `->singleFile()` — one attachment per post (a new upload replaces the old one), since Instagram/YouTube each need exactly one image/video and multi-image carousels aren't built yet. The Launches `Composer` (`WithFileUploads`) is the only UI that uploads to it. There's no conversions/thumbnails pipeline configured — the media UI shows original files directly.

### Publishing pipeline: Laravel queue + scheduler replaces Temporal

`posts:dispatch-due` (`app/Console/Commands/DispatchDuePosts.php`, scheduled every minute in `routes/console.php`) queries every organization for posts in the `Queue` state with a due `scheduled_at` **and a non-null `integration_id`**, bypassing the tenancy scope (`Post::withoutGlobalScope('organization')`) since it runs with no authenticated user. This single poller covers both Postiz's "autopost" and "missing post recovery" Temporal workflows — a post that was somehow skipped just gets picked up on the next run, no separate recovery logic needed.

`PublishPostJob` (`app/Domain/Posts/Jobs`) takes only a post ID, not the model — it re-fetches fresh state at execution time so in-flight jobs survive deploys/queue restarts rather than carrying a stale serialized snapshot. 5 retries, backoff `30,120,600,1800,3600` seconds, `WithoutOverlapping` keyed by post ID to guard against the poller double-dispatching for a still-running job. Each failed attempt records a typed `PostError` (`token_expired` for `RefreshTokenException`, `platform_error` for `BadBodyException`); `failed()` (retries exhausted) additionally marks the post `Error`.

It resolves the actual provider via `SocialProviderManager::driver($post->integration->provider)` — see the Integrations section below. A post with no `integration_id` is a Phase 2-style plain draft, not eligible for dispatch at all.

### Integrations layer (`app/Domain/Integrations`)

One class per platform implementing `Contracts\SocialProviderContract` (`key()`, `label()`, `socialiteDriver()`, `scopes()`, `connect()`, `refreshToken()`, `checkValidity()`, `post()`), registered in `config/social-providers.php` — adding platform #4 is "one class + one config line" via `SocialProviderManager`. `AbstractSocialProvider` implements the shared `connect()` (find-or-create the `Integration` row from a Socialite user) and a `request()`/`assertSuccessful()` helper that maps failed HTTP responses to `RefreshTokenException` (401) or `BadBodyException` (anything else failed).

Real providers lean on **Socialite's own OAuth dance** rather than reimplementing it — `IntegrationConnectController` (`app/Http/Controllers`) is a generic `redirect()`/`callback()` pair driving whichever provider's `socialiteDriver()`/`scopes()` say to use. `LinkedInProvider` uses the `linkedin-openid` driver plus the `w_member_social` scope (personal-profile posting only — org-page posting needs LinkedIn's separate Marketing Developer Platform partner approval) and posts via LinkedIn's `/rest/posts` API. `XProvider` uses Socialite's built-in `x` driver (OAuth2 + PKCE, already includes refresh-token support) plus `tweet.write offline.access` scopes, posting via `/2/tweets`. All connect flows were verified for real: connecting redirects all the way to the platform's live OAuth authorize endpoint with correctly merged scopes — only real `client_id`/`client_secret` env vars are missing until you register developer apps on each platform.

**Important gotcha:** `connect()` returns `Integration|Collection` (not just `Integration`) — Facebook Login only surfaces Pages, not a personal profile, and one login can manage several Pages, so `FacebookProvider::connect()` discovers all of them via `/me/accounts` and returns a `Collection`. `InstagramProvider` reuses the *exact same* Facebook Login (Instagram publishing has no separate login) but reads each Page's linked `instagram_business_account` instead of the Page itself, and authenticates with the Page's own token. Because both need their own redirect URI, they're each registered as a **distinct Socialite driver** in `AppServiceProvider::boot()` (`Socialite::extend('instagram-facebook', ...)` wrapping the same `Two\FacebookProvider` class) rather than both using the literal `'facebook'` driver name — otherwise they'd collide on `config('services.facebook.redirect')` and Instagram connects would silently redirect back to Facebook's callback. `YouTubeProvider` has the identical problem with `'google'` (already used by `SocialAuthController`'s login flow) and is fixed the same way via a `Socialite::extend('youtube', ...)` wrapping `Two\GoogleProvider`. **If you add a provider that shares a Socialite base-provider class with an existing driver, register a new `Socialite::extend()` name for it — don't reuse the base driver string.**

`YouTubeProvider` and `InstagramProvider` both require the post to have an attached image/video (`$post->getFirstMedia('default')`) — see the media-attachment note below. `FacebookProvider` also uses it, but degrades to a plain text feed post if there's no attachment. YouTube's default API quota is ~10,000 units/day and one video upload costs ~1,600 units — about 6 uploads/day/project, a real operational ceiling to plan multi-tenant rollout around (request a quota increase from Google before onboarding many orgs), not something the code works around.

`FakeProvider` (registry key `fake`) is Phase 3's `FakeSocialPublisher` generalized into the same registry — useful for local dev/tests without real API keys, deliberately excluded from the connect UI and from `IntegrationConnectController`'s allow-list (only real providers are connectable).

`Integration` (org-scoped via `BelongsToOrganization`) is distinct from `App\Domain\Auth\Models\SocialAccount` (Google/GitHub *login* linkage) — don't conflate the two. Access/refresh tokens are stored via Laravel's `encrypted` cast, not custom encryption code.

### Launches: the calendar + composer (`app/Livewire/Launches`)

The first fully real user-facing feature. `Calendar` renders every post that has both an `integration_id` and a `scheduled_at` as a FullCalendar event (`resources/js/app.js`'s `launchesCalendar` Alpine component, `wire:ignore`-wrapped so Livewire's morphing never touches FullCalendar's self-managed DOM). Dragging an event calls `$wire.reschedule()`, which reverts the drag client-side if the post isn't still Draft/Queue server-side. Clicking a date opens the composer prefilled via a `#[Url]`-bound `date` query param; clicking an event opens it in edit mode.

`Composer` embeds TipTap (`postComposer` Alpine component, also `wire:ignore`-wrapped) syncing plain text to a Livewire property via `onUpdate` → `$wire.set('content', ...)` — content is plain text, not HTML, since X/LinkedIn both post plain text. Selecting an integration surfaces that platform's character limit (a plain lookup table, `Composer::CHARACTER_LIMITS`) rather than per-editor config, since there's no rich-content mapping to a specific platform's formatting to worry about yet.

This composer (integration-aware, required target) coexists with Phase 2's plain `/posts` CRUD (no integration, freeform state) rather than replacing it — the latter is still there for drafts not yet tied to a publishing target.

### WhatsApp is a separate feature module, not an Integration (`app/Domain/WhatsApp`)

Deliberately outside `SocialProviderContract`/`config/social-providers.php`/the Launches calendar entirely — WhatsApp's Business Cloud API sends targeted template messages to opted-in contacts, not "posts" to a feed, so forcing it into that abstraction would be wrong, not just awkward. Four models: `WhatsAppAccount` (org-scoped via `BelongsToOrganization`, the connected phone number), `WhatsAppContact` (an opted-in recipient), `WhatsAppBroadcast` (one template send), `WhatsAppBroadcastRecipient` (per-recipient delivery log) — only `WhatsAppAccount` has its own `organization_id`; the other three inherit tenant isolation transitively through it, same pattern as `PostComment`/`PostError` through `Post`.

**Important gotcha:** all four model class names snake_case to `whats_app_*` under Eloquent's naming convention (`Str::snake('WhatsApp')` splits on the internal capital A), not the `whatsapp_*` the migrations actually use — every model has an explicit `protected $table` override, and every `hasMany()` that would've guessed `whats_app_*_id` for its foreign key has an explicit second argument. If you add a new WhatsApp model, you'll hit the same thing.

Connecting an account is **manual entry** (WABA ID / Phone Number ID / permanent access token pasted in after the user completes Meta's Embedded Signup themselves), not an OAuth redirect/callback — Embedded Signup's JS SDK flow needs Meta App Review regardless, so a manual flow is no more limited in practice and far simpler to build. Sending (`SendWhatsAppBroadcastJob` → `SendWhatsAppBroadcast` action) is queued, not synchronous, since a broadcast can fan out to many recipients over the network; the Livewire component creates the broadcast + one `pending` recipient row per selected contact first, then dispatches the job, which calls Meta's `/messages` endpoint once per pending recipient and records success/failure individually rather than failing the whole broadcast on one bad number.

### AI Agents: hand-rolled tool-calling chat, not Postiz's Mastra (`app/Domain/Agents`)

Postiz's agent feature runs on Mastra (a Node/TS agent framework, no PHP equivalent) with a `postiz` agent, a Postgres-backed memory store, and a Mastra-specific tool-loader/registry. This is a **clean-room rebuild** of the same capability (chat that lists channels, generates images, and schedules posts on the user's behalf) as plain OpenAI function-calling, hand-rolled rather than framework-driven — architectural ideas only, no ported code, same rationale as the rest of this project (see the top of this file).

Two models: `AgentThread` (org-scoped via `BelongsToOrganization`, belongs to the `User` who started it, optional `title`) and `AgentMessage` (`role`: user/assistant/tool, `content`, `tool_name`/`tool_call_id`/`tool_calls` — inherits tenant isolation transitively through its thread, same pattern as `PostComment` through `Post`). Every step of a turn (the user's message, each assistant tool-call request, each tool's result, the final reply) is persisted as its own `AgentMessage` row, so a thread can be replayed exactly as it was sent to OpenAI — not just the final visible text.

`App\Domain\Agents\Support\AgentConversationService::respond(AgentThread $thread)` is the tool-calling loop: build the system prompt + full message history from persisted `AgentMessage` rows, call the configured chat provider, and if the model requests tool calls, execute each one and feed the JSON result back as a `tool`-role message, looping (capped at `config('agents.max_tool_iterations')`) until the model replies with plain text. Tools are one class per capability implementing `Contracts\AgentToolContract` (`name()`, `description()`, `parameters()` as a JSON Schema, `handle(array $arguments, Organization $organization, User $user, AgentThread $thread)`), registered in `config('agents.tools')` — same registry-array extensibility pattern as `config/social-providers.php`. Current tools: `GenerateImageTool` (generates an image and adds it to the org's media `'library'` collection), `SchedulePostTool` (creates a `Post` via the existing `CreatePost` action — draft or queued, never publishes directly). Video generation and customer/group segmentation (both present in Postiz's real tool set) are deliberately not built yet, same "ship the core, defer the rest" call as the Polotno editor.

There used to be a third tool, `ListIntegrationsTool` (`list_channels`), listing the org's connected channels — removed as a real latency fix, not a bug fix: it was a pure read-only, org-scoped lookup, but offering it as a tool meant every turn that needed channel info paid for a full extra model round trip (decide to call it → tool runs → decide what to do with the result) just to fetch data that's already known before the model says anything at all. `AgentConversationService::systemPrompt()` now inlines the connected-channels list directly into the system prompt instead, so the model never needs to ask.

**Chat provider is swappable** (`config('agents.chat_provider')`, `AI_CHAT_PROVIDER` env, `openai` or `gemini`) — `AgentConversationService` depends only on `Contracts\ChatCompletionContract`, bound to `OpenAiService` or `GeminiService` in `AppServiceProvider::register()`. Both normalize their provider's response into the same `ChatCompletionResult`/`ChatToolCall` DTOs, so the conversation loop, tool execution, and message persistence never see an SDK-specific shape. `GeminiService` is a plain `Http`-facade wrapper (no official Google PHP SDK exists, same reasoning as `FalService`) that translates our internal OpenAI-shaped wire messages into Gemini's `contents`/`functionDeclarations`/`functionResponse` format — notably Gemini has no `system` or `tool` role (system prompt is a separate top-level `systemInstruction` field; tool results are a `user`-role turn with a `functionResponse` part), which is why `AgentMessage`'s `tool_name` is threaded into the shared wire format even though OpenAI's own request shape doesn't need it (`OpenAiService` strips it back out before calling the API).

**Important gotcha:** Gemini's `functionCall.args` and `functionResponse.response` fields are protobuf `Struct`s (JSON objects), but `json_decode($x, true)` collapses both `'{}'` and `'[]'` to the same empty PHP array, and `json_encode([])` always renders `[]`, never `{}` — a no-argument tool call or a no-result tool response would otherwise silently send the wrong JSON shape and Gemini 400s with `"Proto field is not repeating, cannot start list."` `GeminiService` `(object)`-casts both before encoding to force object serialization regardless of emptiness. `Http::fake()`'s decoded `assertSent()` body can't distinguish `{}` from `[]` either (same collapse) — the regression test for this checks the raw request body string instead.

**Important gotcha:** `respond()`'s loop must build the message history via a *fresh* `$thread->messages()->orderBy('id')->get()` query, not the cached `$thread->messages` relation property — `$thread->messages()->create()` (what each loop iteration uses to persist a step) does not update an already-loaded relation cache, so a plain `foreach ($thread->messages as ...)` would show every iteration after the first the exact same stale snapshot from before the loop started, missing its own prior tool calls entirely. Hit for real in production: the model called the (since-removed) `list_channels` tool five times in a row and never once progressed to `generate_image`, because from its point of view every round looked identical - it had no way of knowing it had already called anything.

**Important gotcha:** tools run inside a queued job with no authenticated user, so `SchedulePostTool` must pass `user_id` explicitly into `CreatePost::execute()` — `Post::booted()`'s `auth()->id()` fallback resolves to nothing outside a web request, and `posts.user_id` is NOT nullable (unlike `integration_id`). `CurrentOrganization::set()` (for `Post`'s `BelongsToOrganization` auto-fill of `organization_id`) still applies here exactly as it does in `PublishPostJob`.

**Important gotcha:** four separate timeout/expiry values have to nest in strictly ascending order, or `generate_image` calls against `gpt-image-1` (which routinely take well over 30 seconds) fail or double-run: `config('openai.request_timeout')` (the `openai-php/laravel` HTTP client timeout, 90s) < `ProcessAgentMessageJob::$timeout` (150s, overrides Horizon's supervisor-level 60s default per-job) < both `WithoutOverlapping`'s `expireAfter()` (200s — must outlive the job or its lock can expire mid-run and let a duplicate job start) and the Redis queue connection's `retry_after` (200s — must outlive the job or a worker can consider a still-running job "lost" and requeue it onto a second worker). Hit for real in production as a raw `cURL error 28: Operation timed out after 30002 milliseconds` calling `https://api.openai.com/v1/images/generations` — the package's 30s default HTTP timeout was simply too short, and fixing only that one value would have just moved the failure to whichever of the other three was tightest. `AgentTest::test_timeout_values_nest_correctly_for_slow_image_generation` asserts the whole chain rather than hardcoding any individual value, so tuning one of these later without adjusting the others fails loudly.

**Important gotcha:** `Chat`'s `getIsWaitingProperty()` (which gates the `wire:poll` fallback covering a Reverb outage/dropped event) used to treat any non-User last message as "the turn is done" — but `respond()`'s loop persists an `AgentMessage` after *every* step of a multi-round tool-calling turn (each tool_calls request, each tool result), not just at the end. That flipped `isWaiting` false the instant the *first* such message appeared (typically a tool_calls placeholder), stopping polling well before the model had produced its final reply — every remaining message in that turn then depended entirely on its own Reverb broadcast arriving, with zero fallback if one was ever dropped. Hit for real in production as "sometimes I have to refresh the chat window to see the answer." Fixed by keeping `isWaiting` true through Tool-role messages and Assistant messages that still carry pending `tool_calls` — only a plain-text Assistant reply (no `tool_calls`) actually ends a turn.

**Important gotcha:** `schedule_post`'s `scheduled_at` used to require the model to supply an already-UTC-converted ISO 8601 datetime itself — but the model has no reliable way to know either the actual current date (nothing anchored "today" for it) or the organization's UTC offset, and got real production requests wrong ("3 PM Kuwait time" silently stored as 3 PM UTC, three hours off; other posts landed on the wrong day entirely and simply didn't appear on the Launches calendar, which renders around the real current date). Fixed two ways: `AgentConversationService::systemPrompt()` now injects the actual current date/time in the organization's own timezone (`now($organization->timezone)`) so relative phrases ("today", "in 2 hours") resolve against a real anchor instead of a guess; and `SchedulePostTool` now takes a plain local date-time string in the org's own timezone and converts it to UTC server-side (`Carbon::parse($value, $organization->timezone)->setTimezone('UTC')`), mirroring `Calendar::reschedule()`'s existing pattern for the identical problem — the model is no longer asked to do timezone math at all. Separately, `SchedulePostTool` also now defaults `media_id` to the thread's most recently generated image when the model omits it (a real symptom: posts scheduled with no image despite one having just been generated a couple of tool calls earlier in the same turn) — the same "don't rely solely on the model correctly threading context forward" reasoning behind inlining the connected-channels list into the system prompt instead of a tool call (see above). This required adding `AgentThread $thread` as a fourth parameter to `AgentToolContract::handle()`, since `SchedulePostTool` needs to query the thread's own message history.

**Performance note:** two changes specifically targeted response latency, not correctness. (1) Removing `list_channels` as a tool (see above) cuts a full extra model round trip off nearly every scheduling turn. (2) `OpenAiService::generateImage()` now passes an explicit `config('agents.openai_image_quality')` (default `medium`) to `gpt-image-1` — without it the request fell back to OpenAI's own default, which in practice renders slower than a social-post image needs; trading a bit of visual fidelity for materially faster generation. The single biggest remaining lever is FAL.ai (`FAL_KEY` env var) - `GenerateImageTool` already prioritizes it first when configured, and it's typically dramatically faster than `gpt-image-1`.

Three thin support services back the tools: `OpenAiService` (wraps `openai-php/laravel` for both chat-completions and image generation), `GeminiService` (see above for chat; also does image generation, see below), and `FalService` (a plain `Http`-facade wrapper for FAL.ai's `fal.run` REST endpoint — no official PHP client exists, and it's a single synchronous POST, so a full SDK would be overkill). `GenerateImageTool` picks a provider in priority order: FAL first if `FAL_KEY` is configured (generally cheaper/faster), then Gemini if `AI_CHAT_PROVIDER=gemini` (so a Gemini-centric setup doesn't also need an OpenAI/FAL key), then OpenAI's Images API as the final fallback. Gemini's image generation is native to certain chat models themselves (the "Nano Banana" family, `config('agents.gemini_image_model')`, default `gemini-2.5-flash-image`) via a normal `generateContent` call with `generationConfig.responseModalities: ['TEXT', 'IMAGE']` — not the separate Imagen API, which is deprecated (shut down 2026-08-17) and was never used here.

Frontend is `app/Livewire/Agents/{Threads,Chat}.php` — a thread list and a per-thread chat view. Sending a message (`SendAgentMessage` action) persists the user's `AgentMessage` and dispatches `ProcessAgentMessageJob` (takes a thread ID, not the model, same deploy-safety reasoning as `PublishPostJob`) rather than calling OpenAI synchronously from the request. On permanent job failure (retries exhausted), `ProcessAgentMessageJob::failed()` writes a visible "Sorry, something went wrong" assistant message rather than leaving the user staring at "Thinking..." forever.

As of Phase 8, replies arrive over Reverb (see "Real-time chat via Laravel Reverb" below) instead of the original `wire:poll`-only design the plan called for at Phase 6 - the `Chat` component's `wire:poll` (conditional on `getIsWaitingProperty()`, true while the last message is still the user's) is kept as a passive fallback in case the websocket connection drops, not the primary delivery mechanism anymore.

### Auth

Fortify (registration/login/password reset/2FA) + Jetstream (Livewire stack, teams) + Socialite (Google/GitHub). A single `REGISTRATION_DISABLED` env flag (read via `config/features.php`) gates both Fortify's registration feature and the Socialite auto-register path in `App\Domain\Auth\Actions\SocialLoginService` — setting it unregisters `/register` entirely (404), not just hides the link. `App\Domain\Auth\Models\SocialAccount` tracks Google/GitHub login linkage and is unrelated to the later `Integration` model for actual social-media *publishing* connections — don't conflate the two.

### Billing

Cashier's customer/subscription migrations were retargeted from `users` to `organizations`, including the subscriptions table's FK column (`organization_id`, not `user_id` — Cashier's `ManagesSubscriptions` relation derives the FK from the Billable model's class name via `getForeignKey()`, so this isn't cosmetic). `config/billing.php` maps Postiz's STANDARD/PRO/TEAM/ULTIMATE tiers to Stripe Price IDs. `App\Domain\Billing\Http\Controllers\StripeWebhookController` extends Cashier's own webhook controller to additionally sync `organizations.subscription_tier` from subscription events, so feature-gating can read a plain column instead of querying Stripe/Cashier tables per request. Cashier's own route registration is disabled (`Cashier::ignoreRoutes()` in `AppServiceProvider`) in favor of routes defined in `routes/web.php` pointing at this app's own controller, kept under the same route names (`cashier.webhook`, `cashier.payment`) Cashier normally uses.

### Public API + developer OAuth apps (`routes/api.php`, `app/Http/Controllers/Api/V1`)

Two distinct auth mechanisms protect `/api/v1/*`, matched via `auth:sanctum,api` (Laravel tries each guard in the list in order): **Sanctum** personal access tokens for a user's own first-party API keys (Jetstream's built-in "API Tokens" UI, enabled via `Features::api()` in `config/jetstream.php` — the profile page's `hasApiFeatures()` block had to be added to `resources/views/profile/show.blade.php` by hand, since it was never published while the feature was off), and **Laravel Passport** as a full OAuth2 authorization server for third-party developers who register their own app against the platform (Postiz's `OAuthApp` concept). Both share the same four ability/scope strings — `read`/`create`/`update`/`delete` — defined once for Sanctum via Jetstream's role permissions (`JetstreamServiceProvider::configurePermissions()`) and mirrored for Passport via `Passport::tokensCan()` in `AppServiceProvider`, so `routes/api.php`'s `abilities:*` middleware gates both token types identically. Requests are also tiered by `organizations.subscription_tier` via a named `api` RateLimiter (also in `AppServiceProvider`, limits in `config/billing.php`'s `api_rate_limits`).

**Important gotcha:** Passport's own `HasApiTokens` trait is deliberately **not** added to `App\Models\User` — its `tokens()`/`tokenCan()`/`createToken()`/`withAccessToken()` method names collide outright with `Laravel\Sanctum\HasApiTokens`, already used there for first-party tokens. This turns out to need no resolution at all: Sanctum's versions of `tokenCan()`/`withAccessToken()`/`currentAccessToken()` just operate on whatever token object is currently set via `->can($ability)`, and Passport's own `AccessToken`/`Token`/`TransientToken` classes all implement that same `can()` contract — so Passport's `TokenGuard` (the `api` guard, `config/auth.php`) authenticates against this model with zero extra code. The one thing that *is* required manually: `User::oauthApps(): MorphMany` — Passport's `ClientRepository::create()` calls `$user->oauthApps()->forceCreate(...)` directly by that exact method name (since `oauth_clients` has no `user_id` column, only a polymorphic `owner_id`/`owner_type` pair, Eloquent can't guess a relation name the way it normally would).

`App\Livewire\Developers\Apps` (route `/developers`) is the Pluma equivalent of Postiz's OAuthApp management screen — register an app (name + redirect URL, confidential-or-public client) via `Laravel\Passport\ClientRepository::createAuthorizationCodeGrantClient()`, see the client ID/secret exactly once, list/revoke apps scoped to `Auth::user()->oauthApps()` (manual ownership check, not route-model-binding, since `oauth_clients` has no tenancy scope of its own). The `/oauth/authorize` consent screen also needed a from-scratch Blade view (`resources/views/auth/oauth-authorize.blade.php`, bound via `Passport::authorizationView()` in `AppServiceProvider`) — Passport v13 ships no default view at all (older versions did), so skipping this binding 500s with "Target [AuthorizationViewResponse] is not instantiable."

The full authorization-code grant was verified for real, not mocked: registered an app through the live UI, drove the actual `/oauth/authorize` consent screen in a browser, followed the real redirect to a genuine authorization code, exchanged it at `/oauth/token` for a real signed JWT access token, and used that token against `/api/v1/posts` — confirming both the scope gate (a `read`-only token correctly got 403 on `POST`) and tenant isolation (results scoped to the token owner's organization) end-to-end.

### Admin panel (`app/Livewire/Admin`, `/admin/*`)

Platform-wide, not organization-scoped: `users.is_platform_admin` (a plain boolean, deliberately **not** in `$fillable` — only ever set directly via tinker/a seeder, never mass assignment) gates a `Gate::define('access-admin-panel', ...)` in `AppServiceProvider`, applied to `/admin/*` via `can:access-admin-panel` route middleware. This is a distinct concept from the per-organization `superadmin`/`admin`/`user` roles (`JetstreamServiceProvider::configurePermissions()`) — those are about what a member can do *within* one organization; this is about operating the SaaS itself, closer to Postiz's own admin screens.

`Errors` lists `PostError` rows across every organization (filterable by type), `Stats` shows organization/user/channel/thread counts plus posts-by-state and recent-error counts. Both bypass tenancy scopes explicitly (`Post::withoutGlobalScope('organization')`, etc., same pattern as `DispatchDuePosts`/`PublishPostJob`) rather than relying on an authenticated user's own organization context, since an admin needs to see everyone's data, not their own. Deliberately plain Livewire components (`WithPagination`, a `forelse` loop) rather than pulling in `rappasoft/laravel-livewire-tables` as the plan suggested for this — every other list in this app (Posts, WhatsApp accounts, Developer Apps) already uses this same simple pattern, and introducing a table package for one screen would be more inconsistency than the nicer sorting/filtering UI is worth.

### Real-time chat via Laravel Reverb (`app/Domain/Agents/Events`, `routes/channels.php`)

Upgrades Phase 6's `wire:poll`-only AI chat to genuine push delivery. `AgentMessage::booted()` fires `AgentMessageCreated` (implements `ShouldBroadcastNow`, not `ShouldBroadcast` — message creation already happens inside a queued job or a request, so queuing the broadcast too would just add a redundant hop) on a private per-thread channel (`agent-thread.{id}`), authorized in `routes/channels.php` by checking the thread's `organization_id` against the requesting user's `currentTeam`. `App\Livewire\Agents\Chat` listens via `#[On('echo-private:agent-thread.{thread.id},.AgentMessageCreated')]` — the handler body is empty; Livewire just re-renders with the freshly-rehydrated `$thread->messages` relation, same as any other Livewire request.

**Important gotcha:** the leading `.` before `AgentMessageCreated` in the `#[On(...)]` string is required. Without it, Laravel Echo assumes the event class lives under the historical `App\Events\*` namespace and never matches this event's actual `broadcastAs()` value, so the listener silently never fires — no error, it just never triggers. Confirmed via the browser: `window.Echo.connector.channels['private-agent-thread.1'].subscription.callbacks._callbacks` showed a bound key of `_App\Events\AgentMessageCreated` before the fix, `_AgentMessageCreated` after.

Reverb needs its own long-running process (`sail artisan reverb:start`), same operational model as Horizon — not auto-started, run it manually when you want live streaming; the `wire:poll` fallback still covers the gap if it's not running. `REVERB_PORT`/`REVERB_SERVER_PORT` are both shifted to 8091 (Reverb's 8080 default was already bound by an unrelated local service) — they have to match each other in local dev since there's no reverse proxy translating between an internal bind port and a public-facing one. Testing channel authorization needs `config(['broadcasting.default' => 'reverb'])` **and** re-requiring `routes/channels.php` in the test, not just the config change — `Broadcast::channel()` registers on whichever driver *instance* was already resolved as default at boot (cached per-name inside `BroadcastManager`), so a runtime config switch alone doesn't move those registrations onto a freshly-created instance. Separately, `phpunit.xml`'s `BROADCAST_CONNECTION=null` (deliberately, so most tests don't need a real Reverb server) resolves to `NullBroadcaster`, whose `auth()` is a total no-op — hitting `/broadcasting/auth` under it always 200s with an empty body regardless of channel logic, so any test of the actual authorization rule has to force the `reverb` driver first.

### Image crop/overlay, not a full Polotno embed (`resources/js/app.js`'s `imageCropper`)

The plan's own reduced scope for Postiz's Polotno-based design editor: "ship a basic Cropper.js-based crop/overlay in v1 instead" — not attempted here as a full canvas editor, since Polotno itself is a commercial SDK needing a paid API key. Cropper.js v2 (a from-scratch rewrite of v1, now Web-Components-based: `<cropper-canvas>`/`<cropper-selection>` custom elements instead of a plain class-based API) runs entirely client-side against the raw `File` the user picked in `Launches\Composer`'s upload input — deliberately bypassing Livewire's own upload lifecycle for the crop preview (`FileReader` + `new Cropper(imgElement)` on file `change`, wrapped in `wire:ignore` so Livewire's morphing never touches Cropper's injected DOM). "Apply Crop" calls `getCropperSelection().$toCanvas()`, converts the result to a base64 PNG, and syncs it to a Livewire property via `$wire.set('croppedImage', ...)`. Server-side, `Composer::save()` prefers `croppedImage` over the raw upload when present, decoding it with the same `addMediaFromBase64()` the AI agent's `GenerateImageTool` already uses.

### Marketplace (`app/Domain/Marketplace`) — schema stub only

Postiz's Marketplace (an organization hiring another to manage/create content) per the plan's explicit "low-priority schema stub" scope: `MarketplaceOrder` (buyer/seller organization, amount, status) and `MarketplaceMessage` (belongs to an order, inherits tenant isolation transitively through it, same pattern as `PostComment`/`PostError` through `Post`) exist as migrations + plain Eloquent models only — no actions, policies, or UI. Deliberately no `BelongsToOrganization`: an order references *two* organizations (buyer and seller), which a single-tenant scope can't express cleanly.

**Important gotcha:** `belongsTo()` guesses its foreign key from the *relationship method's name*, not the related model's class name — `MarketplaceMessage::order()` calling bare `belongsTo(MarketplaceOrder::class)` guessed `order_id`, not the actual `marketplace_order_id` column, and silently returned `null` instead of erroring. Fixed with an explicit second argument: `belongsTo(MarketplaceOrder::class, 'marketplace_order_id')`. Note this is the mirror-image of `hasMany()`'s convention, which *does* derive its guess from the declaring model's class name (and worked correctly here without an explicit argument) — the two relation types don't use the same default-FK rule, which is easy to assume until you hit it.

### Header nav is categorized by product area, not a flat list (`resources/views/navigation-menu.blade.php`)

Pluma's roadmap groups into four product areas — Social, Communications, SEO, Analytics & Reports — reflected directly in the header nav rather than a flat link list. **Social** is a dropdown (built with the existing `x-dropdown` component, `align="left"`, styled to match `x-nav-link`'s active-underline look rather than the account-menu styling `x-dropdown` is normally used for) grouping every already-built marketing-facing feature: Launches, Posts, Media, Integrations, WhatsApp, AI Assistant. Its active state (`$socialActive` in the view) is true when *any* of those routes is active, computed once via `collect($socialRoutes)->contains(fn ($p) => request()->routeIs($p))`, since there's no single `social.index` route to check directly. **Communications**, **SEO**, and **Analytics & Reports** are top-level links to placeholder pages (`resources/views/{communications,seo,analytics}/index.blade.php`) — plain "coming soon" Blade views, no Livewire component, since there's no feature behind them yet (see the phased build order this project follows). This keeps the nav category real and clickable ahead of each phase actually shipping, rather than a dead link or an item that has to be added later. Dashboard, Developers, and the permission-gated Admin link stay top-level, outside the four product-area groupings, since they're platform/account-level concerns rather than a marketing activity. The mobile/responsive nav (`sm:hidden`) can't nest a dropdown the same way, so it instead shows a plain "Social" section-label heading followed by its six links inline, matching the existing non-collapsible section-label pattern already used there for "Manage Organization"/"Switch Organizations".
